# 项目协作与验收

## 先明确需求，再形成实施链

先确认用户当前要求的范围、交付物和验收边界。用户讨论、原话、需求及用户决定只放 `document/`；技术取舍、接口、数据格式、错误行为和兼容性放 `design/`。`document/decisions.md` 不是通用技术决策筐。

未确认需求保持 `draft`；向用户汇总范围、排除项、验收标准和开放问题，经明确确认后才标记 `frozen`。需求来源必须能追溯到用户输入，不能把模板或实现建议当作用户决定。

开发工作按真实依赖组织为：

```text
document/ 用户需求或决策
  → design/ 已批准设计或契约
  → plans/ 已冻结实施与验收方案
  → traceability.json 中的任务和测试
  → validation/<任务号>/report.md 与各轮原始证据
  → progress/ 状态投影
```

方案进入 `plans/` 前须确认工作范围、实施步骤、验收条件及边界；尚在讨论的候选方案保留在相应设计讨论中，不把草稿命名为冻结方案。被替代的草稿若有追溯价值再归档到 `history/`。用户需求、技术设计和实施方案的确认是不同事项，不可相互代替。

治理类任务只需真实来源、交付物与适用验证，不为了格式强造技术设计。简单咨询无需新建任务；一旦登记开发工作包，须具备上述链路。技术实现由开发者或外部 AI 工具执行，Harness 只组织和检查资料，不因计划存在扩大操作权限。

## 唯一事实源与当前状态

关联信息与当前状态统一维护在 `.harness/traceability.json`，字段见[数据契约](data-contract.md)。不要在另一个 JSON、表格或文档中维护第二套独立任务账本。

- `progress/tasks.md`：完整任务状态投影。
- `progress/deliverables.md`：交付物与任务映射投影。
- `progress/dashboard.md`：人类一到两屏的当前摘要，不复制完整任务、运行历史或测试明细。
- `progress/current.md`：标记块由事实源生成；块外保存阅读顺序、恢复上下文、修改边界和未决问题。
- `memory/project.md`：仅存有依据、跨任务有用的稳定事实，不保存即时任务日志或原始对话。

先更新事实源，再运行 `python .harness/tools/sync_views.py --write`；不要手改生成部分来让计数看起来正确。NEXT 与当前工作包必须指向真实任务；阶段、动作和风险据实维护。能力 `verified` 必须有已验收开发任务支持，未知能力不写为已验证。没有真实版本计划就不填 `versions`；无确认范围或总量时不编造百分比。

## 工作包验证

测试策略放 `validation/strategy.md`。每个工作包使用独立目录，固定结论入口为 `validation/<任务号>/report.md`。各轮日志、JSON、资源数据、输入清单、哈希和机器输出放该工作包的 `runs/<轮次号>/` 中，不放 `document/`、公开文档或根 README。

先运行与实现相符的实际验证，再记录。使用 `record_validation.py` 导入真实记录与证据；它不代替执行命令，也不会自动把任务改为通过。记录至少包含候选身份、候选文件哈希、环境、实际命令、退出状态、关键指标、失败或中断轮次、适用边界与原始证据路径。没有执行的命令不能伪造为退出 0。

每轮用新的 `run_id`，已存在的轮次不可覆盖。后续通过时报告仍保留先前失败和中断，说明是否更换候选、环境或范围。修正记录通过新增记录和说明完成，不抹去旧结论。通过记录必须有实际证据；验收条件、当前实现哈希、测试、最新适用通过记录和报告一致时，任务才可标记 `verified` 或 `complete`。`complete` 不自动代表已发布。

Harness 自检只证明所检查资料与关联一致，不证明产品正确。哈希可以发现文件与账本不一致，但不是外部不可变存储，也不能抵御证据和账本同时被改写。

## 交接与检查

重要阶段和跨会话交接使用新文件；至少记录当时状态、结果、实际验证、失败/中断、未完成边界、未提交变更和下一步。交接写成后追加路径、时间和 SHA-256 到 `traceability.handoffs`，更新 `state.latest_handoff` 并重新生成当前状态。不得覆盖旧交接来伪装历史始终正确。

每次资料维护后运行：

```text
python .harness/tools/sync_views.py
python .harness/tools/check.py
```

`check.py` 覆盖目录职责、活动 Markdown 链接、追溯引用、状态投影、最新交接与哈希、公开残留、Git 边界和看板长度。历史快照的旧术语或失效链接仅在明确非当前事实源时允许保留；活动资料不能借历史豁免。

## 产品公开边界

根 README 面向产品用户，公开文档只保留使用说明、操作指南和必要的核心技术介绍。不要将开发计划、测试过程、交接、内部评估或 Harness 路径写入公开 README、源码、构建文件或发布包；尚未形成用户文档时不创建空 `docs/` 来容纳开发资料。

`.harness/` 和 `AGENTS.md` 默认可由用户决定是否同步。保持既有 Git 忽略规则，不因同步选择推断公开许可或发布范围。`project.boundaries.git` 默认 `user-managed`；用户明确选择排除时才改为 `excluded` 并检查实际忽略且未跟踪，工具不会替用户改索引。将额外公开路径和实际发布路径登记到边界配置；也可用 `check.py --release <路径>` 检查本次发布物。未指定发布物必须明确“未检查发布包”，不能以源码检查代替发布检查。
