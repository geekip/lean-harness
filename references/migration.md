# 旧资料迁移

本参考记录模板职责调整，也适用于用户明确授权的已有工程迁移。模板升级不代表用户工程已迁移；不要为了更新 Skill 自动修改其他项目或参考工程。

## 路径映射

| 旧模板路径 | 新职责与处理 |
|---|---|
| `.harness/document/dashboard.md` | `.harness/progress/dashboard.md`，由当前事实源重新生成；有价值的旧版本归档 |
| `.harness/document/engineering.md` | `.harness/design/engineering.md` |
| `.harness/document/development-plan.md` | 仅已冻结方案进入 `.harness/plans/`；旧占位或被替代草稿如需保留则进入 `.harness/history/<迁移号>/` |
| `.harness/document/testing.md` | `.harness/validation/strategy.md` |
| `.harness/document/validation.md` | 拆为 `.harness/validation/<任务号>/report.md` 与原始证据；不能把旧汇总直接认证为合格验证 |
| `.harness/document/traceability.json` | 唯一活动源改为 `.harness/traceability.json`，须审查并转换到 schema 2 |
| `.harness/progress/tasks.md` | 路径不变，内容改由唯一追溯源生成；旧人工记录有价值时先归档 |
| `.harness/progress/current.md` | 路径不变，保留详细恢复信息，增加受检查的生成状态块 |
| `.harness/guide/`（若存在） | 按内容分别进入 design 或 progress，不恢复混合文档筐 |
| 公开目录中的计划、测试过程、交接、内部评估 | 按职责移入内部目录，并为旧公开原文创建 SHA-256 快照归档 |

初始化的新模板不携带旧占位草稿，也不会复制活动文件制造第二套事实源。

上表是职责对应，不是可以直接执行的完整 `moves` 列表。文档分拆、旧汇总转结构化记录、静态看板改生成视图和旧账本升级都需要人工审查；不能仅改路径便认为转换完成。

## 迁移顺序

1. 只读检查现有布局、公开路径、Git 状态、链接和权威来源。决定逐个旧路径的新去向；分拆文档需要人工判断，不能只按文件名机械移动。
2. 仅将可直接移动的独立文件写入 `moves`，目标必须不存在；`public` 可作为人工审阅时的公开来源标注。当前工具对所有被移动或改写文件都保留原文哈希快照，不依赖该标注决定是否归档。先预演：

```text
python "<技能目录>/scripts/migrate_project.py" --target "<项目路径>" --mapping "<映射JSON>"
```

映射形如：

```json
{
  "moves": [
    {
      "old": ".harness/document/engineering.md",
      "new": ".harness/design/engineering.md",
      "public": false
    }
  ]
}
```

3. 审阅碰撞、修改范围、旧公开文件归档及引用修正，确认用户已授权后加 `--apply --id <迁移号>`。工具移动活动文件而非复制，保留原文快照与哈希清单，不修改 Git 索引。原始来源、历史、交接和已有验证材料不参与活动引用改写。
4. 按下面的人工升级步骤转换唯一追溯源并补齐资料，再修正剩余活动引用。工具对已经是 schema 2 的账本自动追加迁移交接并更新最新指针；旧 schema 不会自动升级或登记新式交接。
5. 生成进度投影，运行全套自检；对实际发布物追加 `--release` 检查。记录未完成转换和需要用户确认的事项。脚本输出“路径迁移完成”只代表文件操作完成，不代表信息架构或产品验收已通过。

### 迁移助手的边界

- 只处理显式文件映射，不支持目录整体移动、同路径覆盖或目标覆盖。
- 可将旧 `document/testing.md` 移到尚不存在的 `validation/strategy.md`；不能移动已有 `validation/` 原件，也不能把旧汇总直接移入工作包 `report.md` 或 `runs/` 冒充新式记录。
- `history/` 与 `progress/handoffs/` 不能作为普通文件移动的来源或目标；历史快照由归档步骤创建。被替代草稿需先按历史规则保存原文、映射和哈希，再在授权范围内移除活动副本，不能把草稿移入 `plans/` 假装冻结。
- 不迁移 `project.json`，不批准需求/设计/方案，不认证旧证据。自动引用处理覆盖本地 Markdown 链接和追溯字段中的文件路径；普通文字、其他格式、动态路径和语义引用仍需人工检查。
- 发生中断时先检查已执行变化和 `history/<迁移号>/` 的原文快照，不复用已有迁移号覆盖记录，也不盲目重跑。

## 旧 schema 的人工升级

1. 在改写前保存旧 `project.json`、追溯源及要替换的视图原文快照与 SHA-256，登记旧新对应关系；迁移脚本已经归档的原文无需再复制一份。现有交接和验证原件保持原文。
2. 对照[数据契约](data-contract.md)审查旧条目。保留真实需求、用户决定和稳定 ID；分开技术设计与冻结方案，并补足来源和批准依据。缺失信息列为待确认，不为通过检查补造记录。
3. 将唯一活动追溯源改为 `.harness/traceability.json` 的 schema 2。初始化缺失的集合和 `state`，逐条转换已有引用；旧完成结论若缺少当前候选、验收条件或证据，保留其历史说明，并将当前任务置为符合实际的未验收状态。不要将旧 `released` 等状态直接机械映射成 `complete`。
4. 将 `project.json` 更新为 schema/layout 2，保留原项目身份、来源及真实时间，补入概述与边界配置。此步骤只是数据格式转换，不是项目已经通过审查的声明。
5. 审阅后补齐本 Skill 的新目录说明和可信工具，不覆盖根 README、用户资料、既有交接或证据。`current.md` 保留恢复上下文，在适当位置放入唯一一对 `<!-- harness:state:start -->` / `<!-- harness:state:end -->` 标记；清除旧手维护的状态副本，避免与新块竞争。
6. 如本轮尚无新式迁移交接，追加记录说明已转换、未转换与需要重新验证的内容，在账本登记实际哈希并更新最新指针。运行 `sync_views.py --write` 生成看板、任务、交付映射和状态块，再运行 `check.py`；检查错误须按真实资料修正，而非放宽完成条件。

需要重新验收的工作用新的工作包验证轮次留证。旧失败或中断不删除；满足新记录要求前，当前能力和完成度不能借旧汇总声明已验证。

历史目录 README 必须声明 `historical: true` 和“非当前事实源”。每次迁移的 `migration.json` 记录 `old`、`new`、`sha256` 和 `snapshot`，旧公开材料必须有可核查原文快照；不得覆盖已有历史记录。历史失效链接和旧术语只在快照内保留，不回写到活动资料。

迁移助手自动修正 Markdown 链接和追溯字段中的文件引用，不盲目替换普通文字或行内代码里的路径，以免改写用户原话。输出的 `review_text_references` 列出仍提及旧路径的活动文件：逐项判断它是需要更新的当前指引，还是应保留原文的用户答复、历史来源或示例。

迁移助手负责路径、引用和快照，不替代旧追溯结构到新结构的语义审查；在新链路完整前不宣称项目迁移通过。
